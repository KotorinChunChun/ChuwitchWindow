# テスト計画

関連: [v0.2.2-quality-gates.md](v0.2.2-quality-gates.md), [v0.2.2-test-cases.md](v0.2.2-test-cases.md), [v0.2.2-D01-test-infrastructure.md](v0.2.2-D01-test-infrastructure.md)

## 背景

ウィンドウ移動は OS の状態に依存する。すべてを E2E で試すと結果が不安定になり、CI を安定して運用できない。自動テストは純粋計算、ルール、CLI パース、React の表示ロジックに集中する。

## 目的

人手必須を次に限定する。

- 実 HWND の移動（DPI、RDP、ゲーム全画面、管理者）
- グローバルホットキーの OS 登録衝突
- UAC
- 物理/仮想ディスプレイの抜き差し
- トレイ、WebView 破棄、メモリ
- Authenticode（未実施）

## レイヤ

| 層 | ツール | 対象 | 実行 |
| --- | --- | --- | --- |
| Unit | cargo test / Vitest | rule, config, geometry, CLI parse, restore_plan, URL allowlist, ruleUtils | 毎回 |
| Integration | cargo test（モジュール間、Win32 なし） | MovableSet フィルタ + mapping 計算 | 毎回 |
| UI | Vitest + Testing Library | タブ切替、ダイアログ、除外 JSON パースエラー表示 | 毎回 |
| E2E | 0.2.2 では手動チェックリスト。中期に Tauri ドライバを検討 | シフト1回 | リリース前 |
| 生成 | fixtures builder（D01） | モニタ2〜6、窓0〜50 | テスト内 |

採用: Vitest, Testing Library, 自前 fixture（Faker 相当）。  
不採用（0.2.2）: Jest, MSW, Playwright, Storybook, pytest, SQLite。

Playwright は「設定画面がブラウザなら」使えるが、価値の本体が OS なので投資対効果が低い。中期の D07 ポップアップで再検討。

## Definition of Ready（工程共通）

- 設計書が対象ファイル・関数・入出力例を書いている
- 影響するテストケース ID が TASK から参照できる
- DECISIONS のブロッカーに未回答のままスコープを広げていない
- 手動確認が必要な項目が「手動」と書いてある

## Definition of Done（工程共通）

- 設計書の完了条件チェックが全部 true
- `cargo test` と `npm test` がグリーン
- 追加した公開関数に正常・異常・境界が1つ以上
- README / DEV の当該記述が実装と一致
- 手動項目が TEST_CASES の手順どおり作者または実装者が1回実施
- コミットメッセージがユーザー規則に従う（ユーザーがコミットを指示したとき）

## 人手で残る仕様（減らした結果）

残してよい:

- RDP 全画面シーケンスの体感
- スタートアップ（タスクスケジューラ）
- 管理者ウィンドウが一般権限から動かないこと
- トレイアイコン
- ホットキーと他アプリの衝突

減らす（自動化する）:

- 除外ワイルドカード
- CLI 文字列
- スナップ/比率計算
- Undo の分岐選択
- orphan 判定
- URL 許可

（D06 非実施のため URL allowlist テストは 0.2.2 に含めない。代わりに OFF-* で fetch が無いことを見る。）
