# 現状分析

調査日: 2026-08-30。ソースと文書の事実のみ。未コミット変更は RDP 全画面キー送出の修正（`window.rs`）と計画文書。

方針は [v0.2.2-req.md](../v0.2.2-req.md) に回答済み。次リリースは **0.2.2**（信頼性）。実装は別途。本ファイルは調査時点のコード実態である。

## 1. 製品が何か

ChuwitchWindow は Windows 10/11 向けの **マルチモニタ一斉入れ替えツール** である。タスクトレイ常駐し、グローバルホットキーまたは CLI で、開いているウィンドウ群をモニター間で巡回・交換・退避・集約・整列する。

作者の原体験（[USERS_GUIDE.md](../../docs/USERS_GUIDE.md)）は「正面モニタの秩序を崩さずに、サブモニタの作業セットと入れ替えたい」である。Windows 標準の `Win+Shift+矢印`（1枚だけ移動）、仮想デスクトップ（モニタを増やさない）、PowerToys FancyZones（配置効率）は、この需要を満たしていない。

現在の出荷版は **v0.2.1**（タグ済み）。`main` は origin より 2 コミット先行（RDP 全画面移動と除外トグル同期）。

## 2. 技術構成（事実）

| 層 | 実装 |
| --- | --- |
| 本体 | Tauri 2 + Rust + windows-rs 0.52 |
| 設定 UI | React 18 + TypeScript + Vite 7 + Tailwind CSS v4 |
| 常駐 | トレイアイコン。設定ウィンドウは閉じると破棄（WebView2 のメモリ回避） |
| 設定 | `%APPDATA%\kotorichun\chuwitchwindow\config.json`（`directories::ProjectDirs`） |
| ログ | `%LOCALAPPDATA%\kotorichun\chuwitchwindow\logs\`（起動時にディレクトリ削除） |
| 配布 | NSIS インストーラ + 単体 exe。identifier は `com.kotorichun.chuwitchwindow2` |
| テスト | Rust の `#[cfg(test)]` のみ。フロント・CI・E2E なし |
| ライセンス表記 | README はフリーウェア。ルートに MIT の `LICENSE`（2026-08-30 追加） |

README の設定パス `%APPDATA%\com.kotorichun\chuwitchwindow` は誤り。正は NSIS hooks と同じ `kotorichun\chuwitchwindow`。

### v0.2（[v0.2.1-req.md](v0.2.1-req.md)）— 出荷済

ピン留め、除外ルール（JSON + ワイルドカード）、エスケープ、ギャザー、整列ポップアップ、CLI（single-instance 経由）、設定 I/O、PATH 登録、ログ表示、GitHub 更新確認（コード上は残存。0.2.2 の D09 で削除予定）、Ctrl+Tab、フルスクリーン/最小化のルール統合。v0.2.1 のトレイ・スタートアップ・マップ見た目修正も入っている。

ギャップ:

- README の CLI 例は `--shift-next` と `--swap 1 2`。実装は `--rotate-cw` と `--swap=N`
- `trigger_action` は rotate/undo/swap のみ。pin/escape/gather/arrange が欠ける
- 整列の障害物回避は「最大の単一矩形」に削る簡易アルゴリズム
- ピン留めは HWND の HashSet。プロセス終了後の掃除が無い（無効ハンドルが残る）

### v0.3（[v0.3.0-req-draft.md](v0.3.0-req-draft.md)）— 決定により採用しない

ウィンドウサイズ変更ダイアログ、モニタ左上座標の手入力、ドラッグによる OS 配置変更、シリアル番号ベースの配置プロファイル。コードは未着手のまま。決定 Q1-A / Q2-A により実装しない。モニタの `serial_number` は EDID ではなく PnP DeviceID の部分文字列（現状の事実）。

OS 側の配置変更時のマップ再読込は v0.2 で `display-changed` として部分実装済み。切断時のウィンドウ回収は 0.2.2 の D04。

### 導入しないと決めた機能（PLAN_REJECT.md）

レイアウトスナップショット、単体ウィンドウ移動、ウルトラワイド仮想分割、OSD、タイトルバーマウス、ポインタ追従。OSD は v0.1.1 で廃止済み（capabilities に `osd` ウィンドウ名が残っている）。

## 4. 強み

1. **需要が一点に絞られている。** 「画面ごと入れ替える」は競合がほぼ無い。
2. **キーボードファースト。** 常駐ツールとして正しい。設定を開かずに価値が出る。
3. **実環境の泥臭さに手が届いている。** DPI 混在、スナップ、RDP 全画面、管理者ウィンドウ、除外ルール。
4. **メモリ方針が文書化されている。** トレイ時は WebView 破棄。常駐 10MB 級、設定オープン時 250MB、というトレードオフを作者が理解している。
5. **ルールエンジンは純粋関数でテストされている。** `rule.rs` は小型モデルでも触りやすい。
6. **設定の前方互換。** `#[serde(default)]` と rule schema migration がある。
7. **ワンショット CLI。** Stream Deck 連携は製品の拡張軸として既に正しい。

## 5. 弱み

1. **人手確認前提。** フロントテストゼロ、CI ゼロ、E2E ゼロ。ウィンドウ移動の正しさは実機目視。
2. **文書と実装の食い違い。** CLI 引数、設定パス、DEV.md の構成図、RELEASE_GUIDE が汎用テンプレ、バージョンスクリプト削除。
3. **製品境界が揺れ始めている。** SPECv0.3 はディスプレイ設定アプリ化。PLAN_REJECT と衝突しうる。
4. **設定 UI の学習コスト。** 除外ルールが JSON 直接編集。初心者導線が「ピンしてから提案」以外に薄い。
5. **フィードバックが意図的に無い。** ピンの成否が分からない（SPEC どおり）。誤操作に気づきにくい。
6. **アクセシビリティ未着手。** ダーク固定、コントラストは概ね良いが ARIA・フォーカスリング・高コントラスト未設計。

## 6. 技術的負債

| ID | 負債 | 影響 |
| --- | --- | --- |
| TD-01 | `handle_rotate` / `swap` / `escape` / `gather` がフィルタと履歴 push を複製 | 除外条件を1箇所直すと他が残る |
| TD-02 | `MoveAction.new_rect` が rotate/swap では old のコピーのまま | Undo 設計が中途半端 |
| TD-03 | Undo が `SetWindowPos` のみ | 最大化ウィンドウが通常化して戻る |
| TD-04 | `csp: null` と `allow-all` 権限 | 設定 WebView が緩い |
| TD-05 | `open_url` が任意文字列を `cmd /C start` | コマンドインジェクション面 |
| TD-06 | identifier `...chuwitchwindow2` と設定ディレクトリ名の不一致 | サポート時に迷子 |
| TD-07 | `serial_number` が本物のシリアルではない | SPECv0.3 プロファイルの前提が崩れる |
| TD-08 | ホットキー判定のネストが深い | キー追加でバグりやすい |
| TD-09 | トレイ左クリックは既存 WebView があるときだけ show | 破棄後はダブルクリックが必要（v0.2.1 意図か不明） |
| TD-10 | `dev/` が gitignore、release.ps1 削除 | リリースが個人マシン依存 |
| TD-11 | capabilities に使っていない `osd` | 権限表面の残骸 |
| TD-12 | `trigger_action` と CLI とホットキーが3入口 | 実装漏れが起きている |
| TD-13 | ピンのグローバル Mutex + テストが共有状態 | テスト平行実行で壊れうる |
| TD-14 | Framer Motion はダイアログのみ | 依存の割に用途が狭い |
| TD-15 | GitHub JWT 付き画像 URL が README に残る | 期限切れで画像が死ぬ |

## 7. 将来の課題

- マルチモニタの個体識別（EDID）。抜き差し後にグループ色が別モニタへ付く可能性がある。
- Windows の 1/3 スナップ、FancyZones、PowerToys Workspaces との共存。
- フルスクリーンゲーム + 管理者 + 別仮想デスクトップの同時発生。
- WebView2 ランタイム非インストール環境（単体 exe 利用者）。
- Authenticode 未署名による SmartScreen。
- 作者が Rust 非専門家かつ AI 実装。抽象化が厚いと再改修不能になる。

## 8. リスク

| リスク | 深刻度 | 内容 |
| --- | --- | --- |
| 製品拡散 | 高 | SPECv0.3 を無審査で実装すると「入れ替えツール」ではなくなり、保守面が急増する |
| 回帰 | 高 | 自動テスト不足のまま機能追加すると、RDP・DPI・除外の特殊経路が壊れる |
| ディスプレイ破壊 | 高 | OS モニタ座標の書き換えは、複製モードや無効出力でデスクトップを飛ばせる |
| セキュリティ | 中 | 管理者常駐 + 任意 URL 起動 + CSP なし |
| 配布 | 中 | 署名なし、リリーススクリプト消失 |
| サポート | 中 | 設定パス文書誤り、CLI 文書誤り |
| メモリ | 低〜中 | 整列ポップアップも WebView。フォーカス外れで閉じる設計は正しいがリークに注意 |

## 9. 今のコードが小型モデル向きかどうか

向き: `rule.rs`、`config.rs` の migration、`arrange::calculate_layout`（純粋関数 + テストあり）。

不向き: `hotkey.rs` の巨大 if 連鎖、`logic.rs` の Win32 混在、`window.rs` の unsafe 列挙、設定 UI の巨大コンポーネント（ExclusionPanel / SettingsPanel は未分割）。

方針: 新機能の前に「入口を1つにする」「Win32 を薄いアダプタに置く」「計算は純粋関数 + フィクスチャ」へ寄せる。これが AI 実装容易性とテスト容易性を同時に上げる。
